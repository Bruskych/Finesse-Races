### Использованные источники

### Возникшие проблемы

- Сложность локализации целевого события в API фреймворка: Из-за разветвленной иерархии событий Minecraft Forge и наличия множества смежных классов жизненного цикла (в частности, разделения между логическими сторонами и сетевыми фазами подключения) ручной поиск требуемого события среди десятков аналогичных интерфейсов в официальной документации затягивал процесс отладки.

### Решение

- Автоматизация поиска и анализа точек внедрения (Hooks): Для ускорения первичного анализа структуры API фреймворка был применен метод автоматизированного поиска с использованием нейросетевых аналитических инструментов (LLM). На основе заданных критериев (клиентский контекст, момент завершения загрузки мира и игрока) система локализовала подходящие типы событий из исходного кода Forge (`ClientPlayerNetworkEvent` и `TickEvent.ClientTickEvent`).
- Полученные результаты были вручную сопоставлены с официальной документацией и исходным кодом фреймворка (источник S005), после чего выбран оптимальный алгоритм отложенного вызова интерфейса через главный поток исполнения.

## 20.09.2026 - Реализация масштабируемого GUI с использованием Nine-Slice Rendering (Изменения в API - Remedy Core)

### Выполненные действия

- Исследован механизм Nine-Slice Rendering, предоставляемый классом `GuiGraphics` в Minecraft 1.20.1.
- Планировалось использовать ванильный метод `blitNineSliced(...)` для создания масштабируемых панелей интерфейса выбора расы (`RaceSelectionScreen`).
- Проведено тестирование метода на собственной текстуре размером 17×17 пикселей с границами по 5 пикселей.

### Использованные источники

- S003
- S004

### Возникшие проблемы

- При использовании ванильного метода `blitNineSliced(...)` центральная часть текстуры заполнялась некорректно.
- Вместо растягивания центрального участка Minecraft повторял его по горизонтали и вертикали. В результате на увеличенной панели появлялись повторяющиеся элементы текстуры, что не соответствовало требуемому внешнему виду интерфейса.

### Решение

- Для решения проблемы был разработан собственный метод `renderNineSlice(...)` в библиотеке `Remedy Core`.
- Метод создан на основе принципа работы ванильного `blitNineSliced(...)` и реализации Nine-Slice, используемой в моде EMI.
- Исходная текстура разделяется на девять частей: четыре угла, четыре границы и центральную область.
- Углы сохраняют исходный размер 5×5 пикселей, границы сохраняют толщину 5 пикселей, а центральная область растягивается до необходимого размера панели.
- Созданный метод был вынесен в `GuiRenderHelper`, чтобы его можно было повторно использовать в других элементах пользовательского интерфейса.
- Полученный метод применен в `RaceSelectionScreen` для создания трех масштабируемых панелей интерфейса.

### Использованные источники

### Возникшие проблемы

- При использовании обычной отрисовки элементов непосредственно внутри `Screen` было неудобно управлять отдельными панелями и размещать внутри них другие интерактивные элементы.

### Использованные источники

### Возникшие проблемы

- Возникла проблема с созданием собственного типа урона от воды и воспроизведением отдельного звука при его получении.
- Требовалось, чтобы игрок при получении созданного типа урона воспроизводил специальный звук вместо стандартного звука получения урона.
- Для реализации этого поведения необходимо было изменить логику, используемую ванильным классом Player.

### Решение

- Создан собственный тип урона `WATER_DAMAGE` в отдельном классе FineDamageTypes.
- Создан собственный звуковой ресурс и зарегистрирован через FineSounds.
- Для изменения поведения ванильного класса Player создан PlayerMixin.
- Mixin перехватывает вызов метода getHurtSound() и проверяет, был ли урон нанесён созданным типом WATER_DAMAGE.
- Если используется собственный тип урона, вместо стандартного звука возвращается зарегистрированный звук WATER_DAMAGE_HURT.
- Такой подход позволил добавить собственное поведение к существующей ванильной механике без изменения исходного кода Minecraft.

## 24.10.2026 - Добавлена новая система стартовых наборов для рас

### Выполненные действия
- Разработана дата-ориентированная (data-driven) система стартовых наборов на базе `SimpleJsonResourceReloadListener`, позволяющая гибко настраивать выдаваемые предметы, броню и эффекты зелий через JSON-файлы датапаков.
- Создан контейнер данных `RaceStarterKit`, инкапсулирующий логику хранения предметов с использованием `NonNullList`. Внедрено безопасное копирование объектов (`ItemStack.copy()`), предотвращающее перекрестную модификацию (shared memory mutation) предметов в оперативной памяти между разными игроками.
- Реализован обработчик `StarterKitHandler` для безопасного физического распределения экипировки. Разработан алгоритм вытеснения: если целевой слот занят сторонним предметом, он безопасно перемещается в свободную ячейку инвентаря, а при его заполнении — выбрасывается в игровой мир (Drop), что полностью исключает безвозвратную потерю вещей.
- Создан сетевой пакет `SyncStarterKitsS2CPacket` (Server-to-Client) для синхронизации конфигураций наборов. Реализована сериализация сложных объектов (NBT-данных и свойств зелий) в бинарный буфер (`FriendlyByteBuf`) для их последующего рендеринга в клиентском графическом интерфейсе выбора расы.
- Внедрена многоуровневая защита от уязвимостей и ошибок форматирования:
    1. Защита от дублирования выдачи набора с использованием `PersistentData` (NBT-тегов игрока).
    2. Валидация входных данных (Safe Parsing & Clamping): автоматическое ограничение количества предметов их максимальным размером стака и лимитирование уровней эффектов до ванильных значений (0-255) для предотвращения сетевого переполнения (byte overflow).
    3. Отказоустойчивость парсера: изолированная обработка ошибок в JSON, позволяющая игнорировать неисправные слоты без прерывания загрузки остальной части набора.

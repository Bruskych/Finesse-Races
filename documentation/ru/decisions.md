## D000 - Выбор приложения для написания кода
Дата: 18.09.2026
Статус: Принято

### Проблема
Необходимо выбрать среду разработки или редактор кода для создания масштабного мода (Finesse Races). Инструмент должен обеспечивать бесшовную работу со сборочной системой Gradle, поддерживать глубокую навигацию по исходному и декомпилированному коду игры, а также предоставлять продвинутые возможности для отладки клиент-серверной архитектуры.

### Рассмотренные варианты
- Visual Studio Code (VS Code)
- Eclipse IDE
- IntelliJ IDEA
- IntelliJ IDEA Community Edition

### Принятое решение
Для разработки проекта выбрана интегрированная среда IntelliJ IDEA (коммерческая версия Ultimate Edition, легально используемая в рамках бесплатной студенческой образовательной лицензии).

### Обоснование
- Анализ декомпилированного кода: Разработка модов требует постоянного исследования исходного кода самой игры (Minecraft) и ядра Forge. IntelliJ IDEA обладает лучшим встроенным декомпилятором Java-байткода и системой поиска использований (Find Usages), что позволяет понимать, как работает игра изнутри.
- Интеграция с Gradle: IDEA поддерживает композитные сборки, синхронизацию зависимостей и кэширование, минимизируя сбои при компиляции.
- Студенческая лицензия (Ultimate Edition): Статус студента позволяет бесплатно использовать самую продвинутую версию среды. В отличие от бесплатной Community версии, Ultimate Edition предлагает расширенные возможности и скорость работы проекта.

## D003 - Выбор архитектуры
Дата: 18.09.2026
Статус: Принято

### Проблема
Необходимо выбрать оптимальную архитектуру файловой системы и сборочных конвейеров Gradle для разработки крупной соревновательной модификации Finesse Races. Архитектура должна минимизировать технические издержки на настройку среды разработки и позволить сфокусироваться на реализации сложных игровых механик.

### Рассмотренные варианты
- Традиционная монолитная архитектура (Single-Project Build): Проект содержит единую кодовую базу, жестко привязанную к одному загрузчику и одной версии игры.
- Классический мультимодуль (Multi-project Build): Использование одного корневого Gradle-скрипта для управления несколькими подпроектами (общий код, Forge-модуль, NeoForge-модуль).
- Независимые сборочные конвейеры с разделяемой базой (Shared Source Base): Раздельные изолированные проекты для каждого загрузчика, которые в процессе компиляции заимствуют общие исходники из отдельной папки common.
- Строгая многомодульная сборка (на примере архитектуры модов от автора [Obscuria](https://github.com/ObscuriaLithium)): Единый корневой проект с продвинутыми слоями абстракции (фреймворками и скриптами в buildSrc) для массовой одновременной сборки под множество версий и платформ.

### Принятое решение
Для проекта выбрана традиционная монолитная архитектура (Single-Project Build). Исходный код (src/main/java), ресурсы и конфигурационные файлы сборки (build.gradle, settings.gradle) располагаются непосредственно в корневой директории проекта. Вся текущая разработка будет вестись эксклюзивно под платформу Minecraft 1.20.1 (Forge).

### Обоснование
- Масштаб контента: Модификация Finesse Races планируется как очень крупный проект. Фокус разработки должен быть направлен на реализацию асимметричного баланса и сетевой синхронизации, а не на настройку конфигураций сборки.
- Отсутствие необходимости параллельной поддержки: На данном этапе разработка ведется исключительно под Forge 1.20.1. Переход на версию 1.21.1 будет осуществляться в будущем в виде полноценного портирования, поэтому изначальное закладывание сложной мультиплатформенной архитектуры нецелесообразно.
- Избыточная сложность альтернатив:
    - В архитектуре независимых сборочных конвейеров разработчику приходится постоянно делить логику: выносить платформонезависимый код в папку common, а затем писать сложные абстракции и интерфейсы для взаимодействия с платформозависимым кодом загрузчика. Это сильно замедляет написание контента.
    - Строгая многомодульная архитектура (как в Ancient Remnants) требует глубоких знаний Gradle, настройки кастомных плагинов и решения проблем с конфликтующими версиями Java (например, Java 17 для 1.20.1 и Java 21 для 1.21.1). Для соло-разработчика это создает риск поломки среды разработки (IDE) и усложняет компиляцию.
- Индустриальный стандарт для крупных проектов: Монолитный подход с фокусировкой на одну версию платформы - это проверенная временем практика. Именно такую архитектуру используют команды разработки таких гигантских и сложных модов, как Create и Alex's Caves. Это доказывает, что для создания высоконагруженных и масштабных модификаций простая, не перегруженная абстракциями архитектура является наиболее надежной.

## D004 - Выделение базовой логики в независимый API (Remedy Core)
Дата: 19.09.2026
Статус: Принято

### Проблема
По мере роста кодовой базы основного мода (Finesse Races) возникает риск её сильного загромождения. Смешивание высокоуровневой игровой логики (реализация рас, механик) и низкоуровневых утилит (UI-виджеты, рендер, обработка сетевых пакетов) в одном монолитном проекте нарушает принцип единственной ответственности (Single Responsibility Principle). Это усложняет чтение кода, его поддержку, отладку и дальнейшее масштабирование проекта.

### Рассмотренные варианты
- Монолитная архитектура (всё в одном модуле): Написание всего функционала внутри мода Finesse Races.
- Использование существующих сторонних библиотек: Подключение готовых решений (например Blueprint) или другие.
- Разработка собственного API (Remedy Core): Выделение переиспользуемого кода в отдельную независимую библиотеку.

### Принятое решение
Разработка собственного API (Remedy Core).

### Обоснование
- От монолитной архитектуры решено было отказаться из-за высокой связности кода. 
- Использование сторонних библиотек несет риски зависимости от чужого графика обновлений и часто содержит избыточный или же недостаточный функционал. 
- А вот Создание собственного API (Remedy Core) позволяет писать свою логику работы с движком игры, создавать уникальные методы и потом их по многу раз использовать.

## D005 - Стратегия интеграции среды разработки для главного мода и API
Дата: 19.09.2026
Статус: Принято

### Проблема
Для комфортной и быстрой разработки необходимо организовать рабочее пространство так, чтобы зависимый мод (Finesse Races) и библиотека (Remedy Core) могли разрабатываться синхронно. Требуется обеспечить мгновенное применение изменений из кода API в главном моде, избегая разрыва контекста и конфликтов с внутренними механизмами инструментария ForgeGradle.

### Рассмотренные варианты
- Традиционная публикация (mavenLocal): Сборка API в готовый .jar файл и его локальная публикация. Главный мод подключает его как обычную статичную зависимость.
- Композитная сборка (Composite Build / includeBuild): Изолированное подключение Gradle-проектов с подменой зависимостей.
- Многомодульная сборка (Multi-project build / includeFlat): Объединение проектов на одном уровне иерархии файловой системы с общим контекстом сборки.
- Git Submodules: Подключение исходного кода API напрямую в папку src главного мода.

### Принятое решение
Использование многомодульной сборки (Multi-project build) с помощью директивы includeFlat.

### Обоснование
- Традиционная публикация (mavenLocal) не была принята, так как она очень замедляет процесс разработки: каждое минимальное изменение в API требует ручной пересборки .jar файла и перезагрузки проекта.
- Git Submodules смешивает истории коммитов и усложняет управление зависимостями на уровне систем сборки.
- Композитная сборка (includeBuild) изначально рассматривалась как наиболее правильный и красивый подход. Однако в процессе интеграции были выявлены фундаментальные архитектурные конфликты с ForgeGradle версии 1.20.1. Изолированные проекты в композитной сборке теряли доступ к общим локальным кэшам кода Minecraft.
- Переход на includeFlat позволил объединить оба проекта в единое пространство исполнения Gradle. Это позволило инструментарию ForgeGradle использовать общий кэш и маппинги, а среде разработки IntelliJ IDEA - подхватывать исходный код API на лету.

## D006 - Выбор метода масштабирования GUI
Дата: 20.09.2026
Статус: Принято

### Проблема
Необходимо выбрать способ масштабирования / отрисовки графического окна интерфейса, чтобы можно было изменять его ширину и высоту без ухудшения внешнего вида.

### Рассмотренные варианты
* Единая текстура одного размера
* Обычное масштабирование всей текстуры
* Nine-Slice Scaling

### Принятое решение
Для проекта выбран метод Nine-Slice Scaling.

### Обоснование
Выбран метод Nine-Slice Scaling, так как он позволяет изменять размер окна GUI без заметного искажения его углов и границ. Текстура разделяется на девять частей: углы сохраняют свой размер, а остальные части растягиваются в зависимости от размера окна. Благодаря этому одну текстуру можно использовать для окон разных размеров, что упрощает разработку интерфейса и позволяет изменять его размер без создания нескольких отдельных текстур.

## D007 - Выбор контейнерной системы GUI

Дата: 21.09.2026
Статус: Принято

### Проблема
- В процессе разработки GUI было обнаружено, что используемый подход с отрисовкой текстур и методом Nine-Slice Scaling представляет элементы интерфейса только как отдельные графические изображения. Такой подход позволяет изменять размер визуальных панелей, но не создаёт полноценной структуры GUI, внутри которой можно удобно размещать и управлять кнопками, текстом и другими элементами.
- Необходимо было выбрать способ организации интерфейса, при котором панели будут выступать в качестве контейнеров для дочерних элементов, а не только как фоновые изображения.

### Рассмотренные варианты
- Отрисовка текстур и элементов непосредственно в `Screen`
- Использование отдельных координат для каждого элемента интерфейса
- Создание собственных GUI-контейнеров (`GuiPanel`) для группировки элементов

### Принятое решение
Для проекта выбрана контейнерная система GUI с использованием собственного класса `GuiPanel`.

### Обоснование
- `GuiPanel` позволяет представить визуальную панель как отдельный объект интерфейса, содержащий дочерние элементы, такие как текст, кнопки и изображения. Координаты дочерних элементов могут задаваться относительно панели, благодаря чему они перемещаются вместе с ней при изменении её положения или размера.
- При этом Nine-Slice Scaling продолжает использоваться для отрисовки самой панели, но теперь отвечает только за её визуальное представление. Логическая структура интерфейса отделяется от процесса отрисовки текстуры.
- Такой подход позволяет разделить GUI на независимые компоненты и упростить дальнейшее расширение интерфейса. Например, экран выбора расы может состоять из нескольких `GuiPanel`, каждый из которых содержит собственный набор элементов.

## D008 - Адаптивность и масштабирование экранов GUI

Дата: 23.09.2026
Статус: Принято

## Проблема
- У игроков могут быть разные разрешения мониторов и разные настройки масштаба интерфейса (GUI Scale) в игре.
- При больших настройках масштаба или на маленьких мониторах наш интерфейс (широкий экран с тремя панелями) мог не поместиться и выйти за границы экрана. Это привело бы к тому, что часть текста и крайние кнопки были бы обрезаны и недоступны для нажатия.
- Необходимо было выбрать оптимальный метод адаптации интерфейса под любой размер окна без поломки верстки.

### Рассмотренные варианты
- Масштабирование матрицы: визуальное сжатие всего меню (с помощью graphics.pose().scale()). Если интерфейс не влезает, он просто пропорционально уменьшается целиком, как картинка.
- Математическая резина (Подход EMI): динамический перерасчет размеров. Размеры кнопок и шрифтов остаются фиксированными, но сами фоновые панели меняют ширину и высоту в зависимости от свободного места, а элементы внутри сдвигаются ближе друг к другу.

### Принятое решение
- Для проекта выбран подход адаптивности по принципу «Математическая резина».

### Обоснование
- В отличие от масштабирования матрицы, которое сжимает пиксели и делает элементы мелкими и «мыльными», «математическая резина» работает как адаптивный сайт - кнопки и шрифты сохраняют свой нормальный размер, а под экран сужаются только фоновые панели, аккуратно сдвигая элементы ближе друг к другу.
- Совместимость с нашей архитектурой: Система GuiPanel идеально под это заточена. Панели легко меняют ширину через Nine-Slice, а элементы внутри них сдвигаются автоматически благодаря привязке к краям.

## D009 - Выбор системы маппингов для деобфускации исходного кода
Дата: 10.10.2026
Статус: Принято

## Проблема
- В процессе разработки мода Finesse Races и библиотеки Remedy Core возникла сложность с анализом исходного кода движка Minecraft. 
- Стандартные официальные маппинги (Mojang Official Mappings), используемые в Forge по умолчанию, расшифровывают только имена классов и методов. 
- При этом локальные переменные и аргументы методов остаются обфусцированными (например, принимают вид p_49823_). 
- Это делает код неинформативным, заставляет угадывать назначение параметров методом проб и ошибок, а также лишает разработчика доступа к встроенной документации (Javadocs), что критически замедляет реализацию сложных игровых механик.

### Рассмотренные варианты
- Официальные маппинги Mojang (Official): Оставить стандартную конфигурацию Forge. Плюс - максимальная стабильность. Минус - нечитаемые аргументы методов и отсутствие Javadoc.
- Маппинги MCP (Mod Coder Pack): Использовать старый стандарт маппингов, создаваемый сообществом. Минус - устаревший формат, который редко и медленно обновляется для современных версий игры (1.20+).
- Маппинги ParchmentMC: Использовать современный инструмент, который выступает надстройкой над официальными маппингами Mojang. Плюс - полная деобфускация переменных и добавление Javadoc.

### Принятое решение
Осуществить переход на систему маппингов ParchmentMC для всех модулей проекта (API и главного мода) посредством внедрения плагина Librarian.

### Обоснование
Использование ParchmentMC полностью решает проблему слепой разработки. Такая система автоматически транслирует бессмысленные идентификаторы (p_029372) в семантически понятные переменные (level, pos, state) и интегрирует комментарии разработчиков прямо в среду IntelliJ IDEA.
